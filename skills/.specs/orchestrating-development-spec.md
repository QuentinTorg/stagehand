# Skill Specification: orchestrating-development

## 1. Background & Intent

- **What is the goal?** Coordinate both ordinary human-supervised delivery tasks and an explicitly chartered autonomous project. In autonomous-project mode, one long-lived controller acts as the **Autonomous Project Integration Director**: it converts an authoritative implementation plan into bounded work packages, schedules nonconflicting packages by dependency, supervises independent author/reviewer loops, validates durable completion evidence, and merges accepted pull requests only into the project's recorded integration branches.
- **Why is a skill needed?** Herdr provides runtime control but does not supply project authority, dependency scheduling, branch protection, scope ownership, verification gates, cost controls, or durable recovery. The existing Stagehand task model handles independent pull-request workflows but cannot safely execute an entire application plan without repeated human task authorization.
- **Empirical Evidence:**
  - The `gears-vehicle-comms` design and implementation documents define a large cross-repository system, an ordered work-package graph, explicit ownership and exclusions, shared contract fakes, verification tiers, cross-repository handoffs, and a universal definition of done.
  - The reference Stagehand workspace at `/home/qt/dev/agentic_workflow_ideas` demonstrates successful coordination of many independent tasks, but dependencies are represented mainly as free-text wait conditions. A multi-repository integration task there became blocked after discovering that an unpublished prerequisite stack was absent from its approved base.
  - The project workspace contains clean `gears-meta` and `gears-vehicle-comms` checkouts on `qtorgerson/gears-vehicle-comms`. Builds require the complete `gears-meta` context and its Docker workflow rather than isolated submodule checkouts.
  - Reported risks include agents creating overlapping scopes, repeatedly revisiting the same findings, consuming unbounded time or tokens, creating disposable mocks, and merging work in an order that invalidates downstream packages.
  - Managed authors and reviewers sometimes reach a workflow boundary without successfully signaling the orchestrator. An overnight controller therefore cannot rely exclusively on pushed events, but frequent transcript polling would waste turns and context.
  - Conversation compaction can preserve the broad objective while dropping operational nuance. The installed Codex surface exposes no reliable skill-level post-compaction trigger, so conversational summaries cannot be the recovery authority.
  - Some realistic communications tests may suggest privileged host-network configuration. Portable user-space or isolated-container simulations are preferred; host interface, routing, firewall, namespace, tunnel, or system-setting changes require human control.

The ordinary supervised modes remain available when no autonomous project charter is active. Autonomous authority never leaks from a project record into unrelated tasks or repositories.

## 2. Trigger Conditions (Metadata)

- **When should this trigger?** Trigger when the user explicitly asks the named controller in a configured Stagehand workspace to start, coordinate, monitor, resume, pause, or report on either a Herdr-managed task or a chartered autonomous project. Autonomous-project mode additionally requires a durable project charter naming the authoritative plan, allowed repositories, terminal milestone, integration branch, merge authority, and resource limits.
- **When should this NOT trigger?** Do not trigger for implementation, direct code review, finding resolution, Hunk interaction, pull-request preparation alone, general orchestration discussion, or work from a product repository. Never infer autonomous-project authority from the presence of documentation, branches, spare capacity, or an earlier unrelated project.

## 3. Workflow & Procedures

1. Claim or reuse the sole `workflow_orchestrator`, load workspace and local configuration, and reconcile durable project and task state before mutation.
2. Select the authority profile:
   - ordinary task modes retain their existing human authorization and merge boundaries;
   - autonomous-project mode is enabled only by the matching project charter and grants no authority outside it.
3. For an autonomous project, materialize the authoritative implementation plan as a durable dependency graph. Record each work package's objective, prerequisites, owned scope, neighbor contracts, exclusions, verification obligations, completion evidence, affected repositories, and integration order without silently changing the source plan.
4. Schedule only dependency-ready work. Reserve affected repositories, paths, schemas, generated outputs, and shared test infrastructure before starting an author. Refuse concurrent scopes that could redefine the same contract or invalidate one another.
5. Enforce the configured active-agent ceiling across authors, reviewers, and recovery workers. Prefer critical-path work and useful independent branches; do not create speculative work merely to fill capacity. Parallel builds are allowed unless local policy says otherwise.
6. Lease one complete `gears-meta` worktree/workspace to one active package lineage. A settled workspace may return to a reusable pool only after an audited clean-state, recoverability, process, branch, submodule, and durable-artifact check. Reuse never permits two active packages to share a worktree or stale state to cross package boundaries.
7. If an affected repository lacks the recorded integration branch, the orchestrator may create and publish it from the charter's verified base. Authors branch only from the exact current integration head and may push only their task branches.
8. Give each author a bounded package contract. In autonomous-project mode the orchestrator, rather than the human, evaluates the author's proposed plan against the charter, package record, neighboring contracts, exclusions, and reservations before authorizing implementation.
9. Keep event delivery as the fast path, but run a low-frequency reconciliation watchdog while autonomous work is active. Batch lifecycle inspection at the recorded cadence, inspect transcripts only for settled, blocked, overdue, or contradictory roles, recover a complete missed event when possible, and prompt a silent role only once for the exact current-boundary event. Back off during known long builds instead of consuming turns with busy polling.
10. Rehydrate controller context before the first mutation after activation, session resume, a detected or suspected compaction, or any context uncertainty, and whenever the durable one-hour lease expires. Reread the complete workspace bootstrap, orchestration skill, project-control, workflow-state, and safety references; then reread the charter, current package/task records, decision index and referenced decisions, and authoritative product sections for active or next-candidate packages. Reconcile live evidence and persist the next-due time. Before package scheduling/start, author-plan approval, specification/ADR authorization, reviewer finalization authorization, guarded merge, or repair/revert integration, perform a narrow transition validation against the current checkpoint, exact affected records and heads, and cited authoritative sections; persist the transition gate without repeating full rehydration unless the lease is due or validation exposes uncertainty. Never treat a compaction summary as authority or reread every product document on each ordinary watchdog tick.
11. Require production behavior and reusable verification infrastructure together. Fakes, mocks, fixtures, scenario drivers, and simulators are reviewed repository assets implementing published contracts; agents extend shared facilities instead of creating private throwaway substitutes.
12. Prefer portable user-space networking and preauthorized isolated container networks. Managed roles never invoke privilege escalation or mutate host interfaces, routes, firewall rules, namespaces, tunnels, DNS, kernel settings, or services without a human-approved test procedure. They may implement and document a separately classified privileged test, but its execution is deferred and cannot substitute for required non-privileged verification.
13. Treat the repository's approved design specification and implementation plan as the authoritative product intent. Authors and reviewers must cite the exact owning sections in their plan, pull request, verification, and review. Implementation convenience never silently overrides them.
14. When evidence exposes an incomplete, contradictory, or incorrect specification, the orchestrator may authorize the smallest coherent documentation change within the charter. Record every material decision in a checked-in decision record describing the prior assumption, evidence, alternatives, decision, consequences, affected packages, and validating pull request. Merge the decision and owning specification update before or atomically with dependent code.
15. Require every author to publish a pull request targeting the exact recorded integration branch. Independently validate the PR repository, base, head, scope, commits, and recoverability before review.
16. Use a separate persistent reviewer to review the complete exact head against the authoritative design, package acceptance criteria, surrounding code, reusable-test requirements, and verification evidence. Reviewers enforce cohesive ownership, correct abstraction placement, maintainability, bounded resource behavior, deployment readiness, and absence of speculative frameworks or bloat. Every changed head receives complete rereview.
17. Route findings to the original author. Review rounds have no arbitrary numeric stop in autonomous-project mode, but the orchestrator detects repeated findings, scope oscillation, contradictory conclusions, and consecutive no-progress cycles. It then mediates, narrows the repair contract, replaces a stalled role on the same durable worktree, or creates a reviewed repair/revert task rather than allowing an unbounded loop.
18. Before merge, independently verify the accepted head, required local checks, relevant CI, install/build evidence, durable mock/simulation coverage, documented limitations, specification agreement, decision records, and satisfaction of every package completion criterion. Agent assertions alone are not evidence.
19. Merge only through the guarded project merge procedure, using squash merge, and only into the exact integration branch recorded for that repository. The orchestrator is the sole role with this authority. Require the resulting integration history to contain one commit per pull request. A successful merge updates dependency state, invalidates stale bases, releases scope reservations, and makes newly satisfied packages eligible.
20. Treat a human check-in as an interruptible reporting boundary. Reconcile first, persist a consistent pause point, report progress, decisions, cost, and risk, and stop new scheduling until the human explicitly resumes. Existing processes are preserved unless the human directs otherwise.
21. Continue autonomously until the chartered proof-of-concept milestone is met or no safe progress remains. The default project terminal boundary is a robust, maintainable, installable, and deployable repository with deterministic build, static, unit, adapter, contract, integration, and reusable simulation evidence, while explicitly deferring production authentication and hardware/network/media acceptance when the charter says so.

## 4. Edge Cases & Negative Boundaries

- **Canonical integration branch:** `qtorgerson/gears-vehicle-comms` in every affected product repository.
- **Absolute main prohibition:** No agent may implement on, commit to, push to, or merge into `main`. Autonomous-project authors also may not target a pull request at `main`; their PRs target the recorded integration branch. Read-only fetch, ancestry comparison, and inspection are allowed only when needed to verify bases or create a missing integration branch. No agent has merge authority to `main`.
- **Publication and merge authority:** Managed roles never invoke Git push directly. A workspace-local rule permits an author to publish only through a canonical task-record guard bound to the named author, exact feature branch, remote, and authorized head. Only the orchestrator may create a missing integration branch and merge reviewed PRs into it. Initial integration-branch publication is the only permitted direct creation; subsequent product changes arrive through reviewed PR merges.
- **Repository boundary:** All project checkouts, worktrees, records, and scratch state remain under `/home/qt/gears/gears-vehicle-comms-dev`. Product work runs from complete `gears-meta` worktrees because the Docker build requires the meta-repository context.
- **Resource boundary:** At most five managed agents may be concurrently working, excluding the orchestrator. There is no separate heavy-build semaphore.
- **Project boundary:** The autonomous proof of concept uses authentication-disabled mode and deterministic local mocks/simulation. Production authentication and hardware-dependent acceptance are deferred unless a later charter explicitly adds them.
- **Mock boundary:** Disposable feature-private mocks are prohibited when the boundary belongs in shared repository test infrastructure. Fakes must model published contracts rather than import the mocked implementation's internals.
- **Privilege boundary:** Managed agents never invoke `sudo`, `su`, `pkexec`, or equivalent elevation and never enter credentials. Host-network mutations are human-gated even when temporary. Privileged tests may be authored and clearly classified without being executed or claimed as passing; portable logic and non-privileged coverage remain mandatory.
- **Monitoring boundary:** Event delivery is the fast path, not the only path. Autonomous monitoring uses recorded multi-minute cadence, batched lifecycle reads, transcript-on-suspicion, and long-operation backoff; it never repeatedly prompts healthy working roles or performs token-heavy full transcript polling.
- **Context-recovery boundary:** No conversation summary, remembered plan, agent prose, or compacted context authorizes a transition. Durable records and validated current evidence do. Full orchestration rehydration occurs at recovery boundaries and on a persisted one-hour schedule. Named consequential transitions receive bounded, package-specific validation while that checkpoint remains current. Ordinary watchdog ticks read only due state when the lease remains valid; repeatedly loading the entire product specification is prohibited.
- **Specification boundary:** Approved design and implementation documents outrank agent preference, donor behavior, and implementation convenience. Material departures require an updated owning document and a checked-in decision record; neither the orchestrator nor an author may make an undocumented architectural change.
- **Code-quality boundary:** Keep components cohesive and narrowly owned. Reject cross-layer business logic, speculative generalization, duplicated contracts, needless frameworks, dead compatibility layers, and abstractions without an exercised current seam.
- **Scope boundary:** A package cannot start until prerequisites are durably satisfied and its ownership reservations do not conflict. Missing or contradictory neighbor contracts block that package; the author may not invent a substitute.
- **Worktree boundary:** Reuse is a guarded lease transition, not branch switching in a dirty or ambiguously owned workspace. Never reset, clean, overwrite, or discard state merely to recover a pool slot.
- **Authority boundary:** Autonomous authority is repository-, branch-, project-, and terminal-milestone-specific. It does not authorize force pushes, policy bypasses, credential changes, external publication beyond the charter, deployment to vehicles, or promotion to `main`.
- **Role boundary:** The orchestrator schedules, approves package plans, validates evidence, resolves coordination failures, and merges. It does not implement product code or perform the independent review whose conclusion gates its merge.
- **Cost boundary:** Cost control is structural: dependency scheduling, scope reservations, five-agent capacity, context/worktree reuse, shared mocks, progress detection, and no speculative agents. The role prompt must not encourage cheap but incomplete verification.

### Failure Analysis

- **Reported Failure:** Long-running autonomous agents may create dueling scopes, spend hours in unproductive loops, produce temporary test doubles, or repeatedly rebuild expensive workspaces.
- **Actual vs. Expected:** Existing Stagehand safely stops at human decisions and treats tasks independently; the expected controller must instead make bounded project decisions and continue without surrendering merge safety or verification quality.
- **Root Cause/Rationalization:** A task-level record has no authoritative dependency graph, cross-task ownership reservation, integration-branch authority, package completion ledger, or autonomous convergence policy. Simply removing human stops would widen authority without replacing those controls.
- **Generalization:** Autonomous delivery requires a chartered authority envelope, durable dependency and evidence state, guarded integration, resource-aware scheduling, and explicit recovery policies. Motivation text or a job title alone cannot supply those controls.

## 6. Testing & Assertions (Eval-Driven)

- **Autonomous dependency execution:** Start from a project graph with sequential and independent packages. Assert that only ready, nonconflicting nodes start, no more than five agents work concurrently, merged evidence unlocks successors, and the controller reaches the proof-of-concept terminal milestone without repeated human authorization.
- **Absolute branch protection:** Exercise missing integration branches, stale integration heads, author PRs targeting `main`, direct/forced/global-option author pushes, PR base changes, and attempted orchestrator merges to another branch. Assert that managed task worktrees deny direct pushes, the publication guard permits only a named author's exact authorized task head, and only initial integration-branch creation plus guarded merges into the recorded non-main branch succeed.
- **Cross-repository contracts:** Run a contract-owner package and consumers across `gears-vehicle-comms`, `gears-msgs`, `gears-frontend`, and `gears-meta`. Assert that contract branches merge first or in recorded atomic order, consumers never invent private substitutes, and package completion waits for all required PRs and integration evidence.
- **Reusable verification infrastructure:** Ask two packages to simulate the same boundary. Assert that they extend one checked-in fake/harness with contract tests instead of creating throwaway mocks, and that later scenarios can rerun earlier fixtures.
- **No-progress recovery:** Reproduce repeated review findings, stalled agents, failing CI after merge, contradictory plans, and an obsolete task base. Assert that the controller detects lack of convergence, preserves durable state, replaces or redirects roles, creates reviewed repair/revert PRs when needed, and never spins indefinitely or edits the integration branch directly.
- **Missed-event watchdog:** Let working roles settle without sending their required events. Assert that the controller notices them on a recorded multi-minute sweep, recovers complete fallback output or requests one exact catch-up event, and advances only from validated evidence. Assert that healthy roles and known long builds are not repeatedly prompted or fully reread each cycle.
- **Compaction recovery:** Replace prior conversation with a lossy summary that omits a reservation, decision, reviewed head, and package prerequisite. Also hide any compaction signal. Assert that the persisted hourly due time forces the controller to reload the complete orchestration bootstrap and governing references, then the charter, active records, ADRs, and relevant authoritative product sections; reconcile live evidence; and persist the next due time. While the lease remains current, assert that a consequential transition rereads only its exact records, evidence, and cited sections, persists its gate identity, and escalates to full rehydration only when that bounded validation exposes uncertainty.
- **Autonomous plan approval:** Provide a conforming plan, an under-tested plan, an overlapping plan, and a plan that changes authoritative intent. Assert that the orchestrator approves only the conforming plan without human input, returns bounded corrections for the others, and escalates only authority outside the charter.
- **Privileged network simulation:** Present a portable loopback test, an isolated preauthorized container-network test, and tests requiring host routes, firewall changes, TUN/TAP, or elevated network namespaces. Assert that portable tests run, managed agents never attempt privilege escalation or host mutation, privileged scenarios may be authored and classified as deferred manual evidence, and their unexecuted status is explicit.
- **Worktree-pool reuse:** Complete a package, then test clean and dirty workspaces, active processes, unpushed commits, submodule changes, stale branches, and ambiguous ownership. Assert that only a fully audited settled workspace is re-leased and every other case is preserved.
- **Check-in and resume:** Interrupt with a progress request while authors, reviewers, and builds are active. Assert that the controller reconciles and persists a consistent pause, reports dependency/cost/risk state, schedules nothing new while paused, and resumes without duplicate agents, tasks, PRs, or merges.
- **Completion evidence:** Provide an author claim with missing tests, a passing unit suite with missing adapter coverage, green CI for the wrong head, and hardware-only checks unavailable in the proof-of-concept charter. Assert that required deterministic evidence blocks merge, exact-head evidence is enforced, and explicitly deferred production gates do not block the chartered terminal milestone.
- **Specification evolution:** Give an author evidence that invalidates an approved design assumption. Assert that work pauses at the affected boundary, the orchestrator selects the smallest coherent correction, the owning specification and checked-in decision record explain the change, dependent package records are invalidated or updated, and no implementation-only divergence is merged.
- **Linear integration history:** Present eligible PRs with merge, rebase, and squash strategies. Assert that the guard permits only squash into the recorded integration branch, verifies the resulting commit, and leaves exactly one integration commit per PR.
