# Agentic Development Workflow: Documentation Outline

## Documentation Conventions

- Number normative documents with two-digit prefixes to establish reading order.
- Organize documents from high-level workflow concepts to lower-level component details; use workflow order to break ties.
- Give each concept one authoritative document. Other documents summarize only enough to establish context, then use GitHub-compatible relative Markdown links to the authoritative source.
- Keep the initial documents concise, targeting roughly 50–100 lines where the subject permits.
- Classify each document as a workflow contract, artifact contract, skill contract, or integration contract. Do not imply that every workflow area requires a runtime component or skill.
- Give detailed documents a consistent structure where applicable: purpose, responsibilities, inputs, outputs, lifecycle, boundaries, and open questions.
- Keep unsettled decisions in [`90-decisions-and-open-questions.md`](./90-decisions-and-open-questions.md) rather than presenting them as normative behavior.

This document owns system-wide intent, lifecycle, runtime control layers, and boundaries. It links to detailed documents without implying that each one is separately implemented.

### [`05-human-workflow.md`](./05-human-workflow.md)

**Purpose:** Provide the human-facing playbook for operating persistent author and reviewer sessions.

- Role establishment and continuity
- Natural-language workflow transitions
- Skill trigger matrix
- Automatic routing versus explicit invocation
- Optional slash-command or prompt aliases
- Handoff visibility
- Session replacement and recovery
- Human control boundaries

This document owns the expected user experience and prompt-level transitions. It does not define skill internals or orchestrate agents.

This document owns change-intent artifacts and their lifecycle. The initial implementation is a reusable template, not a skill.

### [`20-authoring.md`](./20-authoring.md)

**Purpose:** Define the authoring workflow contract from accepted change context through review handoff.

- Change-context input
- Scope control

- Draft pull-request creation
- Review handoff
- Interrupted-work recovery

This document owns implementation-stage behavior. It is guidance for ordinary coding-agent operation, not a separate authoring skill in the initial implementation. - Scope restrictions

This document owns finding adjudication and code-fix behavior when the original author resumes implementation, and is one of the three planned initial skills. It references [`30-reviewing-code.md`](./30-reviewing-code.md) for the finding contract.

### [`50-pull-request-lifecycle.md`](./50-pull-request-lifecycle.md)

**Purpose:** Define the human-controlled workflow contract for the durable GitHub record and its progression from draft to human merge.

- Draft pull-request creation
- Pull-request description as durable change brief
- Description updates after implementation and review
- Risk, testing, limitations, and reviewer guidance
- Ready-for-review transition
- Reviewer readiness recommendation and human-authorized finalization
- Human and team review
- CI and policy ownership
- Squash-merge expectations
- Explicit exclusion of merge execution

This document owns GitHub pull-request state, section authority, and team-facing documentation. The narrow preparation skill implements its authorized mutations without owning the lifecycle policy.

### [`55-preparing-pull-requests.md`](./55-preparing-pull-requests.md)

**Purpose:** Define the skill contract that creates the structured draft pull request and applies reviewer-authorized finalization.

- Explicit triggering and near-miss exclusions
- Draft-creation mode
- Finalization mode
- Repository-template compatibility
- Protected intent and section authority
- Inputs, outputs, and validation
- Progressive-disclosure packaging
- External-action and merge boundaries

This document owns how agents prepare and update the pull-request artifact. It implements [`50-pull-request-lifecycle.md`](./50-pull-request-lifecycle.md) without owning review judgment or merge execution.

### [`60-review-adapters.md`](./60-review-adapters.md)

**Purpose:** Define the integration contracts between review analysis and existing external review surfaces.

- Common review-finding contract
- Hunk delivery for private review
- Hunk feedback consumption by the author
- GitHub delivery for teammate pull-request reviews
- Publication authorization
- Avoiding duplicated state
- Adapter failures and recovery

This document owns review transport, not review judgment or fixing policy. The initial implementation reuses Hunk and GitHub rather than creating another review system.

### [`90-decisions-and-open-questions.md`](./90-decisions-and-open-questions.md)

**Purpose:** Preserve non-normative working memory without destabilizing the workflow contracts.

- Confirmed decisions
- Superseded historical ideas
- Unresolved skill-triggering questions
- Receiving-feedback skill disposition
- Future Herdr orchestration
- Candidate tooling
- C++, Docker, submodule, meta-repository, and worktree questions

This document owns unresolved and historical context. Normative documents link here only when an open decision materially affects their contract.

## Future Skill Specifications

Detailed package specifications for the pull-request preparation, review, and finding-resolution skills may later live with the skill implementation. They must link to the authoritative workflow contract they implement and must not restate unrelated workflow requirements. No other workflow area should become a skill without a demonstrated need.
