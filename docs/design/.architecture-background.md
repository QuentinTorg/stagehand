# Agentic Development Workflow: Architecture Background

## Objective

Define a reusable, personally operated workflow for developing one cohesive feature or bug fix at a time with coding agents. The workflow should produce well-reviewed GitHub pull requests that fit ordinary human team practices.

## Guiding Principles

- Human intent and control are authoritative.
- Agents work from an explicit change brief when one is available.
- Implementation may proceed autonomously only within approved boundaries.
- Review is performed by an agent independent from the author before a pull request is marked ready for team review.
- Local review iteration should not create noisy GitHub review history.
- Every change reaches `main` through a human-merged GitHub pull request.
- Pull requests are squash-merged so intermediate branch history may remain iterative.
- Review depth adapts to the changeset's risk and scope.

## High-Level Workflow

1. Establish a change brief and, when useful, an implementation plan.
2. Implement and verify one cohesive change.
3. Open a draft GitHub pull request whose description becomes the durable change brief.
4. A complementary reviewer agent independently reviews the complete changeset.
5. For privately authored changes, deliver review findings through Hunk.
6. Classify findings before returning selected, in-scope findings to the original author.
7. The author resolves selected findings, and the same reviewer performs a complete rereview.
8. Fix, accept, or explicitly defer remaining findings without inflating the pull request.
9. The reviewer recommends readiness and presents the final implementation, risk, testing, limitations, and review context to the human.
10. Once authorized, the reviewer updates the pull request and marks it ready for final human and team review.
11. Let GitHub policy, CI, and the developer control merge readiness and execution.

For another developer's pull request, the same review analysis applies, but approved findings may be published as a GitHub review rather than returned to the local author agent.

## Information and State

- **Change brief:** Authoritative goals, acceptance criteria, constraints, and non-goals.
- **Implementation plan:** Optional local guidance that may evolve during implementation.
- **Review context:** A handoff assembled from the brief, diff, repository guidance, and verification evidence.
- **GitHub pull request:** Durable team-facing record and recovery point.
- **Hunk:** Private local review and feedback transport.
- **GitHub issue:** Optional destination for work explicitly deferred by the human.
- **Git branch and commits:** Implementation state; intermediate commit history need not be polished before squash merge.

## System Boundaries

The workflow uses a complementary author-reviewer pair. The original author remains the implementation agent throughout review-and-fix iterations, while a separate reviewer agent retains review history across rereviews. The human manually initiates and coordinates both agents in the initial design. Pull-request finalization is not a separate role: after a successful final review, the human may authorize the reviewer to update the pull request and mark it ready. The workflow does not own agent scheduling, parallelism, worktree allocation, or terminal management. Herdr or another outer layer may automate the same handoffs in the future without changing the core workflow.

Agent continuity reduces repeated repository discovery and preserves relevant conversation context, but it is not the source of truth. The change brief, branch, pull request, review findings, and verification evidence must still support recovery when either session is lost or replaced.

The workflow must remain compatible with GitHub, local or Docker builds, C++, repositories containing submodules, and normal company CI and branch policies.

The workflow architecture is not itself a single agent skill. Its initial implementation is deliberately small:

- a manual playbook describing the role loop and human checkpoints;
- a reusable change-brief template;
- an explicitly invoked pull-request preparation skill;
- an explicitly invoked code-review skill;
- an explicitly invoked finding-resolution skill; and
- integration guidance that reuses Hunk and ordinary GitHub pull-request operations.

Repository instructions remain the always-on source of repository-specific constraints. Change briefs provide per-change intent, and each task-specific skill loads only for the transition it owns. Authoring and human control remain workflow contracts rather than skills; the pull-request lifecycle is implemented by the narrow preparation skill without becoming an orchestrator.

The human initiates workflow transitions with short, explicit natural-language requests. Skill metadata routes those requests to the applicable skill; skills do not run as background automation. The author role is established by the implementation conversation, while the separate reviewer is assigned once at the beginning of review and normally remains active through rereviews. Optional slash commands or Herdr prompt aliases may provide deterministic shortcuts without becoming part of the portable workflow contract.

## Non-Goals

- Merging pull requests.
- Replacing CI, branch protections, or company policy.
- Encoding company-specific requirements.
- Embedding a multi-agent orchestrator in the core workflow.
- Autonomously producing sequences of unrelated features or pull requests.
- Automatically fixing every valid review observation.
- Expanding a pull request to include tangential cleanup.
- Requiring every implementation plan to become permanent repository documentation.
- Loading the entire workflow specification into every agent context.
- Creating a skill for every workflow stage.
- Requiring slash commands or one specific agent interface.

## Audience and Deployment

The primary users are an individual developer and their coding agents running on a local development workstation. The design should be generic enough for similar developers elsewhere. Teammates consume the resulting GitHub pull requests but are not expected to install or understand the local tooling.

## Open Design Areas

- Persistence of local plans before a draft pull request exists.
- Finding classification, deferral, and automatic-fix eligibility.
- Review-loop limits and escalation conditions.
- Exact pull-request description templates for changes of different sizes.
- Exact trigger wording and progressive-disclosure architecture for the pull-request, review, and finding-resolution skills.
- Whether Herdr or another outer layer should automate the currently manual role handoffs in a future iteration.
- C++, Docker, worktree, meta-repository, and submodule behavior.
